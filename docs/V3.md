# Summernote Gallery v3

Gallery v3 is the greenfield development line for `summernote-gallery`. It is being developed in parallel with the current package so existing installations and persisted content are not silently changed while the new contract is validated.

## Integration boundary

Gallery v3 is a normal Summernote plugin registered as `summernoteGallery`.

The plugin uses Summernote's own lifecycle and UI APIs rather than calling Bootstrap directly. jQuery and Summernote remain host concerns; Gallery does not own the application's UI framework.

The current browser compatibility gate targets Summernote 0.9.1 with:

- `summernote-bs5`;
- `summernote-lite`;
- Chromium;
- Firefox;
- WebKit.

BS4/BS3 remain release-matrix decisions, not assumptions.

## Source adapter

The v3 image picker is backend-agnostic. Applications provide a `GallerySourceAdapter` that returns normalized image records instead of configuring Gallery around one HTTP response shape or server framework.

A normalized image can contain:

```ts
{
  id?: string;
  src: string;
  alt: string;
  title?: string;
  caption?: string;
  width?: number;
  height?: number;
}
```

This keeps transport, authentication, upload policy and API pagination outside the editor plugin.

## Persisted HTML contract

New galleries persist semantic HTML that remains useful without Gallery JavaScript:

```html
<div class="snb-brick snb-gallery"
     data-snb-brick="gallery"
     data-snb-version="3"
     role="group"
     aria-label="Image gallery">
  <figure class="snb-gallery__item">
    <img src="/images/mountain.jpg"
         alt="Mountain"
         data-snb-image-id="mountain"
         loading="lazy"
         decoding="async">
    <figcaption class="snb-gallery__caption">Mountain caption</figcaption>
  </figure>
</div>
```

Editor controls, modal state and runtime-only styles are not part of persisted content.

## Legacy content

Older Gallery releases persisted source data inside `data-brickdata`, usually with a `selectedImages` array and a flat list of `<img>` elements.

V3 deliberately does **not** rewrite that markup when an editor is opened. Existing database content must remain byte/DOM-stable unless the host application explicitly chooses to migrate it.

The v3 source exports two migration helpers:

- `parseLegacyGallery(element)` reads known legacy Gallery markup without mutating it;
- `migrateLegacyGallery(element)` returns a new semantic v3 node when the legacy markup can be understood.

The caller owns replacement and persistence. A migration can therefore be reviewed, run in a controlled batch, or applied only when a document is explicitly edited.

Unknown, malformed or empty legacy data returns `null`; it is not guessed or destructively rewritten.

## Release gate

Gallery v3 is not stable until all of the following are proven:

1. strict TypeScript checks and package build pass;
2. package/export smoke tests pass;
3. standalone browser tests pass on the documented Summernote matrix;
4. multiple editors remain isolated;
5. destroy/recreate does not duplicate lifecycle state;
6. create/edit participates correctly in Summernote history;
7. keyboard/focus and loading/error states are accessible;
8. persisted HTML round-trips without editor-only artifacts;
9. legacy markup behavior is covered by tests and documented;
10. package entrypoints and peer dependencies are finalized.

Until those gates are green, v3 artifacts and APIs should be treated as development interfaces rather than stable release promises.
