# Summernote Gallery v3

Gallery v3 is the current release-candidate source line on the public `master` branch. It modernizes the plugin contract while preserving repository/package identity and keeping migration of legacy persisted content explicit rather than automatic.

Source readiness does not imply registry publication. npm versions and GitHub Releases remain separate maintainer-controlled actions.

## Integration boundary

Gallery v3 is a normal Summernote plugin registered as `summernoteGallery`.

The plugin uses Summernote's own lifecycle and UI APIs rather than calling Bootstrap directly. jQuery and Summernote remain host concerns; Gallery does not own the application's UI framework.

The maintained compatibility matrix proves Summernote 0.9.1 with:

- Bootstrap 3;
- Bootstrap 4;
- Bootstrap 5;
- Summernote Lite;
- Chromium;
- Firefox;
- WebKit.

The cross-repository Summernote Bricks harness builds and packs the current public Gallery package before running those browser scenarios.

## Source adapter

The v3 image picker is backend-agnostic. Applications provide a `GallerySourceAdapter` that returns normalized image records instead of configuring Gallery around one HTTP response shape or server framework.

A source image can contain the semantic persisted image fields plus optional editor/source metadata:

```ts
{
  id?: string;
  src: string;
  alt: string;
  title?: string;
  caption?: string;
  width?: number;
  height?: number;

  // source-only metadata
  createdAt?: string;
  mediaType?: string;
  path?: string;
}
```

`createdAt` and `mediaType` can be used by source filtering. `path` drives deterministic folder-tree helpers and dialog folder navigation. These source-only values are not serialized into Gallery HTML.

The source request supports text search, structured filters, cursors and cancellation with `AbortSignal`.

## Optional upload adapter

Hosts can provide a `GalleryUploadAdapter` when upload controls should be available:

```ts
interface GalleryUploadAdapter {
  upload(files: File[], signal?: AbortSignal): Promise<GalleryImage[]>;
}
```

Gallery owns the editor interaction, cancellation lifecycle, normalization and selection of returned images. The host owns the endpoint, authentication, storage provider and server implementation.

Closing or destroying the Gallery dialog aborts in-flight uploads. File objects, credentials and transport state are editor/runtime-only and are never persisted.

## Folder navigation

Folder grouping is derived from source-only image `path` values. Gallery normalizes paths, builds a deterministic tree, resolves exact folders and displays accessible root/parent/child navigation when folders exist.

Only images belonging directly to the selected folder are displayed. Selection survives navigation. A new search or completed upload resets navigation to the root so newly returned images are visible.

The source module exposes the same deterministic primitives to hosts:

- `normalizeGalleryPath`;
- `buildGalleryFolderTree`;
- `galleryFolderPath`;
- `filterGalleryImagesByFolder`;
- `findGalleryFolderNode`.

Folder paths and controls remain editor-only.

## Persisted HTML contract

New galleries persist semantic HTML that remains useful without Gallery JavaScript:

```html
<div class="snb-brick snb-gallery"
     data-snb-brick="gallery"
     data-snb-version="3"
     role="group"
     aria-label="Image gallery">
  <figure class="snb-gallery__item">
    <img src="/images/mountain.jpg"
         alt="Mountain"
         data-snb-image-id="mountain"
         loading="lazy"
         decoding="async">
    <figcaption class="snb-gallery__caption">Mountain caption</figcaption>
  </figure>
</div>
```

Editor controls, modal state, runtime-only styles, source filters, folder paths and upload transport data are not part of persisted content.

## Legacy content

Older Gallery releases persisted source data inside `data-brickdata`, usually with a `selectedImages` array and a flat list of `<img>` elements.

V3 deliberately does **not** rewrite that markup when an editor is opened. Existing database content remains unchanged unless the host application explicitly chooses to migrate it.

The v3 source exports two migration helpers:

- `parseLegacyGallery(element)` reads known legacy Gallery markup without mutating it;
- `migrateLegacyGallery(element)` returns a new semantic v3 node when the legacy markup can be understood.

The caller owns replacement and persistence. A migration can therefore be reviewed, run in a controlled batch, or applied only when a document is explicitly edited.

Unknown, malformed or empty legacy data returns `null`; it is not guessed or destructively rewritten.

## Release gate

The v3 source line has already proven the engineering gates required for source readiness: strict TypeScript, package/export checks, deterministic installs, semantic round-trip behavior, legacy migration tests, multi-editor lifecycle, accessibility/focus behavior and the maintained Summernote/browser matrix.

A public package release still requires explicit maintainer review of version/tag, package contents, migration notes and release checklist. Source merges do not authorize npm publication or GitHub Release creation.
